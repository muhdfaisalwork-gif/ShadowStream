# v2.4.41 — Player fix: sandbox removed, hostile providers purged, playback verified

**Date:** 2026-11-01
**Live version:** 2.4.41 (code 281, service worker v50)
**Reported symptom:** `https://ssmoviestvs.site/play/the-last-of-us-2023?season=1&episode=1` showed *"We couldn't find that — We have searched through our providers and cannot find the media you are looking for!"* and could not be recovered from.

---

## 1. Root cause

There were **two independent failures** behind that screen, and one of them was self-inflicted in v2.4.39.

### 1.1 The iframe sandbox broke every provider (v2.4.39 regression)

v2.4.39 added a strict sandbox to the provider iframe as part of the AdShield hardening:

```jsx
sandbox={noAdsEnabled ? "allow-scripts allow-same-origin allow-forms allow-presentation" : undefined}
```

Both providers we ship detect the **presence** of the attribute and refuse to play:

| Provider | Response |
|---|---|
| `player.videasy.to` | *"Iframe Sandbox Detected — This iframe has sandbox restrictions that prevent proper functionality."* |
| `vidstuck.cc` | *"Sandbox Detected — This player is running inside an unsupported sandbox environment."* |

Five token sets were tested side by side in one browser session (`/variants` probe):

| Variant | Result |
|---|---|
| no sandbox attribute | **plays** |
| `allow-scripts allow-same-origin allow-forms allow-presentation` (v2.4.39) | refused |
| `+ allow-popups-to-escape-sandbox` | refused |
| `+ allow-popups +allow-popups-to-escape-sandbox +allow-top-navigation-by-user-activation` | refused |
| `allow-scripts allow-same-origin` only | refused |

The check is presence-based, not flag-based, so no token set works.

A CSP `frame-src ... 'sandbox ...'` directive was also tried as a way to keep popup blocking without the attribute. Chrome **does not enforce** it — a same-origin child frame under that policy still reported `POPUP_ALLOWED`. That path was rejected on evidence, not assumption.

### 1.2 Videasy soft-404s, and the client cannot see it

With the sandbox off (AdShield OFF — the state in the reported screenshot), Videasy loads for real. For The Last of Us it has no source: its own source API `api.speedracelight.com/seed?mediaId=100088` fails repeatedly and Videasy renders its own *"We couldn't find that"* page.

That page is served with **HTTP 200**, so:

- the iframe's `onLoad` fires and `handleEmbedLoaded` **cancels the stall watchdog**;
- no error event ever fires, so the automatic failover never runs;
- v2.4.39 removed the manual "Switch Source" control, so the user had **no way out**.

A cross-origin iframe exposes no playback signal at all. Measured directly on a working provider (VidStuck) and a soft-404 one (Videasy) at t+6s, t+12s and t+20s:

| Signal | VidStuck (working) | Videasy (soft-404) |
|---|---|---|
| `contentWindow.length` | 0 | 0 |
| `contentWindow.location.href` | SecurityError | SecurityError |
| `load` event | ~1s | ~2s |

Identical. **A client-side watchdog cannot tell "playing" from "not found".** That is why the fix cannot rely on the client alone.

### 1.3 Two providers were being served that should never have been

- `player.videasy.to` — loads a popunder tracker (`meatusbyway.cfd/cuid`) and a hostile redirect (`hostile.wonnotscroganisoin.cyou/gd/115848`) **whose payload embeds our own domain** (`https://ssmoviestvs.site`).
- `embed.smashystream.com` — **NXDOMAIN**. It was still in the rotation and in the catalogue.
- `vidsrc.buzz` — hostile host, still being handed to the player from two code paths.

## 4. Honest limitations

1. **The presence probe only works for providers that signal absence with an HTTP error.** NontonGo (502) and Vidlink (500) do; VidStuck, 2Embed, VidSrc and Vidy answer 200 for any title, so the probe cannot see their soft-404s. The manual source switcher is the only safety net there, and that is a browser limitation, not a missing feature.
2. **Popup defence is weaker than the sandbox was.** Without the sandbox attribute, a provider *iframe* can open popups on its own — a cross-origin frame's `window.open` is not visible to our overrides. The mitigations are the AdShield JS guards (which cover our own page), and the fact that the hostile providers are gone from the rotation. Restoring hard popup blocking would require sandboxing, which is exactly what breaks playback.
3. **`v2.4.40` was never deployed.** It would not have fixed this: it promoted VidStuck to #1 but kept the sandbox, and VidStuck refuses sandboxed embeds too. Verified directly.
4. **The version endpoint lagged a release** because `/api/v1/app-version` is served from `version.json` in the R2 bucket, not from the Worker bundle, and the pipeline never published it. Fixed in the deploy workflow.

## 5. Plan reconciliation

The two attached plans were implemented, with one correction:

- **Unified 4-source engine** — TMDB key rotator (3-key pool) was already in place and is intact; provider rotation is now curated instead of blind; the server-clutter goal is met (no server list in the top bar) while keeping a one-tap escape hatch; silent failover is kept for hard failures.
- **Videasy full-catalog / AdShield hardening** — the multi-audio goal is implemented, but on **VidStuck** rather than Videasy. Videasy was the wrong host for it: it refuses sandboxed embeds, soft-404s titles it does not host, and fires trackers that target our own domain. VidStuck carries native dubbed audio (`dubLang`/`dubType`, 13 languages wired) and its own in-player server switcher.
- **Verification** — the script exists and now checks playback viability rather than HTTP 200 alone, and it runs in CI after every deploy.
