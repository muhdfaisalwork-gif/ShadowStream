## A. What changed in v2.4.42, and how it was decided

### A1. The ads are not a bug in our code — they are the provider's own script

The player embeds a third-party provider page in an iframe. The provider serves its ad/popunder script **from its own origin**, not from a third-party CDN. Captured live on the current rotation:

| Request | Role |
|---|---|
| `GET https://vidstuck.cc/vidstuck.js` | the injector, loaded by the provider page itself |
| `GET https://t2f.183nq1tht933j77g.cfd/...` | rotating ad script (host changes every load) |
| `POST https://meatusbyway.cfd/cuid/?f=...` | popunder beacon |
| `POST https://aulete.chequesjuddersearle.qpon/gd/...` | click tracker |
| `GET https://www.googletagmanager.com/gtag/js`, `google-analytics.com/analytics.js`, `static.cloudflareinsights.com/beacon.min.js` | analytics |
| `GET https://users.vidy.st/api/script.js` | the same injector for the Vidy provider |
| `GET https://t2f.<random>.cfd/`, `nifty.<random>.qpon/gd/...` | Vidy rotation, same chain |
| `GET https://soycdn.lol/__ads/vidsrcto.js` | Vidsrc ad script |
| `GET https://tags.crwdcntrl.net/lt/shared/2/lt.iframe.html`, `bcp.crwdcntrl.net/pixels` | Lotame ad frame + pixel (NontonGo and Vidsrc) |
| `GET https://adplox.com/promo/click` | 2Embed ad link |
| `llvpn.com`, `histats.com`, `intelligenceadx.com`, `rtmark.net`, `luugy.com`, `adsco.re` | NontonGo trackers |

Because that script runs **inside the provider's cross-origin frame**, nothing our page does can touch it: page-level JS cannot reach into the frame, Electron's `setWindowOpenHandler` never sees a `window.open` the frame makes, and Android's `onCreateWindow` never sees it either. The only thing that ever blocked it was the iframe `sandbox` attribute, which the provider detects and refuses to play for.

**Conclusion that drove the whole release:** the fix cannot live in the web page. It has to happen in the app, at the network layer, *before* the request leaves the device.

### A2. What the desktop app and the APK now do

Both apps drop the ad traffic before it runs, so the injector never executes and the popunder never opens.

Rules applied in `packaging/windows/app/resources/app/main.js` (`isAdUrl`) and `scraper/build_android_apk.py` (`isAdOrTracker`):

- **By path on the provider's own host** — the host list cannot catch these, the path can:
  `/vidstuck.js`, `/__ads/`, `/cdn-cgi/rum`, `/scripts/vidy.js`, `/api/script.js` (Vidy hosts only), `/lt/shared/`
- **By TLD for the rotating hosts** — the domain changes on every load, the TLD does not:
  `.cfd`, `.qpon`
- **By host** — the third-party list: Lotame, `soycdn.lol`, `adplox.com`, GTM, Google Analytics, Cloudflare Insights, `umami.is`, `llvpn.com`, `histats.com`, `intelligenceadx.com`, `rtmark.net`, `luugy.com`, plus the previously known hostile hosts.

### A3. The subframe guard was corrected from allowlist to denylist

The first implementation kept a list of "player hosts" and denied any subframe navigation outside it. Measuring the live provider chains showed this is unworkable:

```
vidsrc.to/embed/tv/100088/1/1
  -> vidsrc.sh/embed/tv/100088/1-1
     -> stellarconductornexus.com/embed/tv/100088/1/1?vs=...      <- real player
```

The final hop is on a host the provider invents per load, so any allowlist is guaranteed to be incomplete and would have blocked playback. Anime players live on yet other hosts (`animesalt.cx` → `abyssplayer` / `ravok` / `cybervynx` / `autoembed`), so the same allowlist would have blocked **anime** as well.

Both apps now use a **denylist**: ad hosts are dropped at the network layer, which also covers a subframe navigating to one, and unknown hosts are never blocked.

### A4. The web player now switches servers by itself

| Problem (measured) | Fix |
|---|---|
| A flat 16s watchdog cut off providers that were still loading — the three-hop Vidsrc chain measured ~19s cold | Per-provider budget: 20s normally, 32s for multi-hop providers (`watchdogBudgetFor`) |
| The rotation was blind round-robin, so a dead provider was retried on every episode change | Dead-provider memory with a 5-minute TTL; a provider that loads clears its own mark, and the mark expires so a recovered provider returns on its own |
| When every server failed, the user got a silent black rectangle — the failover bar styles existed in `ShadowStream.js` but no JSX ever used them | The bar is now rendered with **Keep waiting** and **Change server** actions; *Change server* opens the server picker directly |

### A5. Web `adShield.js` keyword list expanded

Added the hosts and paths measured above, plus `2embed.skin` to the first-party list (2Embed now redirects `www.2embed.cc` → `www.2embed.skin`, and the old entry was stale). The page-level guard still covers our own page: popups, third-party link clicks, and anything it loads itself. It cannot clean the provider's frame — that is a browser security boundary, not a gap in the implementation.

### A6. A same-origin mirror was built, measured, and removed

A provider mirror was prototyped on the catalog worker: serve the provider's document from our own origin on its real paths (`/embed/...`, `/backend/...`, `/_next/...`), neutralise the ad script with an empty route, and lock the document down with a CSP. It worked for the document and assets, and the ad script was successfully neutralised.

It was still removed, for one measured reason: **the provider's API answers `403 "Sorry, you have been blocked"` to Cloudflare Worker egress**, while the same URL returns `200` from a normal machine. The API sends no CORS headers and no JSONP, so the browser cannot relay it either. A mirror therefore serves a document whose player cannot load its sources — a silent soft-404. Nothing in the client ever pointed at it, and it hijacked `/embed/*` and `/backend/*` on the catalog worker, so it was removed rather than shipped.

Two other web mechanisms were tested and rejected on evidence, not assumption:

- **Chrome's `csp` iframe attribute** (CSP embedded enforcement) — Chrome supports it, but the framed document must opt in. The live error: *"Refused to display 'https://vidstuck.cc/' in a frame. The embedder requires it to enforce the following Content Security Policy … However, the frame neither accepts that policy using the Allow-CSP-From header nor delivers a Content Security Policy which is at least as strong as that one."* The provider does neither, so the frame is refused outright.
- **`sandbox` on the iframe** — presence-based detection by every provider ("Sandbox Detected"); no token combination plays.

## C. The "missing links" defect: the app plays a different title than the one you clicked

### C1. What you saw

Searching "Cowardly Dog" returns exactly one title — **Courage the Cowardly Dog (1999)** — and opening it linked a completely unrelated video. The same class of failure is why country, genre and category pages look like they buffer forever.

### C2. The measurement

The catalogue's internal `id` is **not** the TMDB id. Sampled 35 titles across movie/TV/anime from the live API — **35 of 35 disagree**:

| Catalogue id | TMDB id | Title | Slug |
|---|---|---|---|
| 130899 | **2085** | Courage the Cowardly Dog | `courage-the-cowardly-dog-1999-2085` |
| 40111 | **275102** | The Scandal | `the-scandal-2026-2` |
| 89914 | **1374** | Rocky IV | `rocky-iv-1985` |
| 13132 | **30984** | Bleach | `bleach-2004` |
| 418 | **1429** | Attack on Titan | `attack-on-titan-2013` |
| 431 | **209189** | Solo Leveling | `solo-leveling-2024` |
| 15442 | **969492** | Land of Bad | `land-of-bad-2024` |

### C3. The root cause, in four links

1. **The list endpoints do not return the TMDB id.** The item shape from `/titles` and `/search` is:
   `id, slug, title, year, type, rating, poster, isAnime, scripted, seasonCount, audioLanguages` — **no `tmdbId`**.
2. **The client then guesses, and guesses wrong.** `frontend/src/screens/PlayerScreen.js:146-156`:
   ```js
   if (item.tmdbId && ...) return String(item.tmdbId);      // 148 - absent in list items
   if (item.tmdb_id && ...) return String(item.tmdb_id);    // 149 - absent
   if (item.id && /^\d+$/.test(String(item.id))) return String(item.id);  // 150 - the INTERNAL catalogue id
   if (typeof item.slug === 'string') { const m = item.slug.match(/-(\d{4,9})$/); ... } // 151-154
   ```
   Line 150 hands the internal catalogue id to the API as if it were a TMDB id. Line 151's slug fallback would be right, but it never runs, because line 150 always returns first.
3. **The slug fallback is weak anyway.** Only **7 of 35** sampled slugs end with the TMDB id (`…-10054`, `…-2745`, `…-298168`). For `land-of-bad-2024` or `the-scandal-2026-2` there is no id in the slug at all. So guessing from the slug fixes roughly one title in five.
4. **The worker never validates the id.** `/stream/resolve` accepts any number and turns it straight into a provider URL — no check that it corresponds to the requested title. The availability rows the app already holds contain the **correct** id (`https://vidstuck.cc/embed/tv/2085/1/1`), but the client-side scan at `PlayerScreen.js:455-467` only recognises `vidlink.pro/…`, `video_id=`, `tmdb=` and `tmdb/movie?id=` — **not** the `/embed/tv/<id>/` shape every live provider uses. So the right id sitting in the availability URL is never read.

**The server side already knows about this trap.** `index.ts:2621-2625` carries the comment:

> `// which are always dead: 13082 is our row id, not Charade's TMDB id.`
> `// Titles with no TMDB id therefore get no aggregator mirrors at all.`
> `const tmdbId = title.tmdbId;`

`buildFallbackAvailability()` therefore builds every availability row from the **real** TMDB id — which is why the availability URLs are correct and only the client's own guess is wrong. The source of truth also exists upstream of the worker: the catalogue database stores both `titles.id` (row id) and `titles.tmdb_id` (`scraper/auto_daily_sync.py:89`), and the worker's small detail index already carries `tmdbId: number | null` (`index.ts:431-437`). The id is available everywhere except in the list endpoints the app actually browses.

### C4. The result, concretely

For the title you searched:

| | id used | URL the app plays | what that id actually is on TMDB |
|---|---|---|---|
| Courage the Cowardly Dog | `130899` (catalogue id) | `vidstuck.cc/embed/tv/130899/1/1` | **"Song of Love" (1947)** |
| The Scandal (country=KR) | `40111` (catalogue id) | `vidstuck.cc/embed/tv/40111/1/1` | **"La Blue Girl: Revenge of the Shikima Realm" (1995)** |

And because the worker streams are **prepended** to the availability rows in `PlayerScreen.js:453`+`470-494`, the wrong-title stream is the **first** source — the default one. The correct stream is present but second, so the wrong video wins unless you manually switch servers.

### C5. Why it presents as "missing links" rather than an error

The provider happily serves a page for whatever id it is given. There is no 404, no error event, no console message: the frame loads, and it loads the wrong content. When the id has no content at all, the frame loads an empty player and the watchdog fires — which is exactly the "buffering" you see.

### C6. A second, smaller path to the same wrong title

`downloads/streamapp-worker/src/index.ts:2275` `getFullTitleData()` falls back through prefix matches when an exact slug is not found — `index.ts:2387` (`slug.startsWith(clean)`) and `index.ts:2389` (`clean.startsWith(e.slug)`) — then to any same-name title. A lookup for a title the catalogue does not have can therefore land on a **different** title that shares a name prefix. The name-collision logic just above it (lines 2290-2380) is deliberate and documented and should stay; the prefix fallbacks are the part that can silently substitute a title.

## D. Country / region and category pages

### D1. The APIs themselves are healthy

Measured live:

| Endpoint | Time | Result |
|---|---|---|
| `/api/v1/titles?country=KR&page_size=30` | 1,074 ms | `total: 661`, 30 items |
| `/api/v1/titles?country=US` | — | `total: 11808` |
| `/api/v1/titles?genre=action` | 900 ms | `total: 2575` |
| `/api/v1/titles?genre=animation&country=JP` | 703 ms | `total: 567` |
| `/api/v1/countries-catalog?with_counts=1` | 137 ms | 42+ countries with counts (KR 661 — consistent with `/titles`) |
| `/api/v1/genres` / `/genres-catalog` | — | consistent counts |
| `/api/v1/titles?type=movie` | 517 ms | fine |

The country and genre screens (`CountryDetailScreen.js:243`, `GenreScreen.js:68`) call exactly these and complete. **The country/genre listing is not the problem.**

### D2. Categories *are* broken

`/titles?category=popular` returns six junk titles:

> Popular Serizawa Acts Weird Around Me · Popular Theory · Popular (1999) · Popular (2023) · Popularity Papers · Popular Mechanics

Cause: `index.ts:1585` routes `collection`, `provider` **and** `category` into the same variable, and when no matching collection file exists the worker falls through to a **full-text search for that word** (`searchTitles(col, env, 30)`).

`BrowseScreen.js:174-198` then takes the result: it requests `/titles?collection=<slug>&page_size=60`, and because the junk list is non-empty, the screen uses it and never reaches its proper trending/popular path. So every category tile that is not a real collection file shows search results for the category's name.

### D3. Why country and category pages "buffer"

Both are downstream of the same defect in C:

1. You open a country or category page → a list is shown (the list itself is fine).
2. You tap a title → the client sends the **catalogue id** to `/stream/resolve` → the provider is asked for a different title → the frame loads either the wrong video (C4) or an empty player (nothing indexed under that id).
3. The player then sits on "Optimizing HD stream…" until the watchdog fires, then shows the failover bar.

So the "buffering" is not a slow catalogue and not a slow API — it is the id mismatch, plus the provider page rendering nothing for an id it does not have. Fixing C fixes D3.

### D4. Two smaller sharp edges in the same area

- `getFullTitleData()`'s prefix fallbacks (C6) can substitute a title when a slug misses.
- The catalogue's `id` field has no type distinction from a TMDB id anywhere in the API surface. Nothing stops a caller from sending `id` where `tmdbId` is expected — which is precisely what happened.

## E. Fix plan

Ordered by user-visible impact. Nothing here has been implemented; this is the plan only.

### P0 — one release, stops the wrong-video problem

| # | Change | Where | Acceptance |
|---|---|---|---|
| P0-1 | **Return `tmdbId` in every list item.** The id exists in three places already — the catalogue DB (`titles.tmdb_id`), the worker's small detail index (`DetailIndexEntry.tmdbId`, `index.ts:431-437`) and the availability URLs — it is only the big list item shape that drops it. Either join the detail index into the browse/search response, or export `tmdb_id` in the catalogue snapshot. | worker: item builder used by `browseTitles` and the `/search` route (`index.ts:5669`) | `GET /titles` items contain `tmdbId` equal to `GET /title/{id}`'s `tmdbId` |
| P0-2 | **Stop guessing on the client.** Delete the `item.id` branch; order becomes `item.tmdbId` → `item.tmdb_id` → slug suffix → `null`. | `PlayerScreen.js:146-156` (line 150 removed) | `effectiveTmdb` is never a catalogue id |
| P0-3 | **Read the id that is already in the availability URLs.** Extend the regex to the shapes providers actually use: `/embed/(tv\|movie)/(\d+)`, `/embed/tmdb/(tv\|movie)?id=(\d+)`, plus the existing `vidlink.pro/…`, `video_id=`, `tmdb=`. | `PlayerScreen.js:455-467` | the fallback recovers the id for every sampled title |
| P0-4 | **Validate the id server-side.** In `/stream/resolve`, if `tmdbId` is unknown to the catalogue, resolve it from `slug` → the catalogue's `tmdbId`; reject or correct otherwise, and echo `resolvedTmdbId` + `titleMatch`. | worker `/stream/resolve` (`index.ts:5139`+) | a request with a catalogue id returns the *corrected* id or an explicit error, never a URL for a different title |
| P0-5 | **Guard the source order.** Do not prepend a worker stream whose id does not match the title's id. | `PlayerScreen.js:453`, `470-494` | the default source is always the title's own id |

### P1 — catalogue surface

| # | Change | Where | Acceptance |
|---|---|---|---|
| P1-1 | **`collection` must never fall through to a text search.** Load the collection file or return an empty list; a missing collection is not a search term. | `index.ts:1585` + `searchTitles` fallback | `/titles?collection=popular` returns collection content or empty, never "Popular Serizawa…" |
| P1-2 | **Categories use real endpoints.** `/categories` already returns `trending-today` etc.; point the Browse screen at it and at the real collection list. | `BrowseScreen.js:174-198` | every category tile renders its intended set |
| P1-3 | **Make the prefix fallbacks opt-in.** Keep the documented name-collision rules; move the `startsWith` fallbacks (`index.ts:2387`, `2389`) behind an explicit `fuzzy=1` so a plain lookup never lands on another title. | `index.ts:2380-2392` | a wrong slug 404s instead of opening a different title |
| P1-4 | **Rename the field.** Expose the catalogue key as `catalogId` and keep `id` as an alias for compatibility; `tmdbId` stays the only TMDB field. Prevents the whole bug class. | catalogue snapshot + worker item shape | no API consumer can mistake `id` for a TMDB id |

### P2 — stop it coming back

| # | Change | Where |
|---|---|---|
| P2-1 | **A link-integrity gate**: sample N titles from the catalogue, assert the id embedded in every availability URL equals the title's `tmdbId`, and that `/stream/resolve` never returns a URL for a different title. Run it in CI next to `verify_streaming_resolution.py`. | new `scripts/verify_catalog_link_integrity.py` |
| P2-2 | **A collection gate**: every category/collection slug must return a non-search result set. | same gate file |
| P2-3 | **Runtime mismatch detector**: after the frame loads, compare the provider's own title with the expected title; on mismatch mark the source, auto-switch, and record it. | `ShadowStreamPlayer.js` |
| P2-4 | **Process rule (already used for 2.4.42)**: "build successful" is not "release ready". The gates above must pass before a release is called done. | CI |

### Suggested sequencing

P0-1 → P0-2 → P0-3 are a small, self-contained change that removes the wrong-video symptom immediately (the client stops guessing once the API stops hiding the id). P0-4 and P0-5 close the hole server-side. P1-1/P1-2 fix the category tiles. P1-4 is the structural fix and can ride along. P2 keeps it fixed.

## F. Known limitations after 2.4.42 (stated plainly, not hidden)

1. **In a plain web browser tab, the provider's in-frame ads cannot be removed** without breaking playback. The ad script is same-origin with the provider, the provider will not opt into `Allow-CSP-From`, `sandbox` makes them refuse to play, and the API cannot be proxied from our server (403 to Worker egress). The desktop app and the APK block it at the network layer; that is the working answer for ad-free playback today.
2. **Provider chain hosts rotate** (`stellarconductornexus.com` was one instance). Only the denylist approach is safe for them; an allowlist cannot be maintained.
3. **`downloads/ShadowStream.apk`** (a stale duplicate R2 key from 2026-10-23) still points at an old build. The site serves `ShadowStream.apk`, so nothing user-facing depends on it. Left as-is for consistency with the 2.4.41 release; it should be refreshed or removed.
4. The catalogue itself still contains titles the provider does not host. For those, the player will legitimately find nothing — the failover bar now says so instead of spinning silently, but the fix is a better source list, not a client change.
